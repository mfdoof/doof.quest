Postmortem: every path returned 200

A scanner asked my site for cloud credential files and got 200 OK every time. Nothing leaked. The site was missing a 404 page, so Cloudflare Pages sent the homepage for any path.

$ cat summary

While reading Cloudflare's traffic logs I found one IP asking for about 20 secret files in two seconds, like /credentials.json and /service-account.json. Every request came back 200 OK. A size check showed each one was my homepage. Pages has a fallback for single-page apps: if a site has no 404.html, every unknown path gets index.html. I added a 404 page and put Cloudflare rules in front of the site.

$ cat impact

  • No data was exposed. The site is static and has no secrets in it.
  • The logs were misleading. A 200 on /credentials.json looks like a breach until you check what was actually sent.
  • Scanners that see 200 on everything mark the site as interesting and come back.

$ cat investigation

The requests came from a Google Cloud address. They asked for GCP service-account keys, Firebase admin keys and phpinfo.php, all within two seconds.

A 200 says the server answered, not what it answered with. So I compared a probed path with the homepage:

$ curl -s -o /dev/null -w "%{http_code} %{size_download} %{content_type}\n" https://doof.quest/credentials.json
200 17421 text/html; charset=utf-8
$ curl -s -o /dev/null -w "%{http_code} %{size_download} %{content_type}\n" https://doof.quest/
200 17421 text/html; charset=utf-8

Same size, same type, and the body was my homepage HTML. No file was served.

Then I sorted the week's traffic by source IP. The top one was a server hosted in France: about 3,000 requests in one burst, asking for .github files with the slashes and dots URL-encoded. Encoding is a trick to slip past simple path filters. Pages answered those with redirects and nothing reached a file.

$ cat root-cause

The site had no 404.html. When Cloudflare Pages can't find one, it assumes the site is a single-page app and returns index.html with status 200 for any path that doesn't exist. That's useful for a React app with client-side routes. For plain HTML pages it means every missing file looks like it exists.

$ cat fix

  • Added site/404.html in the site's terminal style, marked noindex. Pages now returns a real 404 for anything that doesn't exist.
  • Added Cloudflare rules so probes are stopped before they reach Pages. The hardening how-to covers those.
$ curl -s -o /dev/null -w "%{http_code}\n" https://doof.quest/notes/nope.html
404

$ cat lessons

  • A 200 isn't proof a file exists. Check the size and content type before deciding something leaked.
  • Know your host's defaults. The SPA fallback was a Pages default I never chose.
  • Read the logs even when nothing is broken. The site worked fine. Only the logs showed the problem.
